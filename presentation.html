1. Problem Statement
The Challenge of Limited Resources
Core Question from Project Specification
“More EVs request charging than the number of available charging points. How can the software limit simultaneous charging?”
1. Physical Limit
The station has a fixed hardware capacity of 3 charging bays. Connecting more vehicles than plugs causes physical overload.
2. Resource Contention
When 5 EVs arrive at the same time, all 5 cannot be granted power immediately. Uncontrolled concurrency causes race conditions.
3. The OS Solution
The software limits active charging to 3 vehicles using a Counting Semaphore, placing remaining cars into a sleep/wait queue.
Say this to Madam "The problem is that demand exceeds capacity. When 5 cars request power for only 3 plugs, software synchronization is required to prevent over-allocation."
2. Core OS Concept
Why a Counting Semaphore?
How It Operates
1. Initialization: sem = Semaphore(3)
Counter is initialized to integer 3 (representing 3 chargers).
2. sem.acquire() [P operation]:
Decrements counter. If counter > 0, thread enters immediately. If counter == 0, thread blocks and sleeps in wait queue.
3. sem.release() [V operation]:
Increments counter and wakes up one blocked thread in FIFO order.
Counting Semaphore vs Mutex
Mutex (Binary Semaphore):
Only permits a single entity (0 or 1). It would force 1 car to charge while 2 bays sit completely wasted!
Counting Semaphore ($N = 3$):
Allows exactly 3 threads to charge concurrently while throttling excess requests. Ensures 100% station utilization without conflicts.
Say this to Madam "We use a Counting Semaphore instead of a Mutex because we have 3 identical resources. A Mutex would only allow 1 car at a time, leaving 2 bays wasted."
3. Unique Implementation Feature
The 4-Stage Charger Lifecycle
The software tracks the exact physical hardware transitions of each charging point:
STAGE 1
Available
Charger is idle, plug docked.
Semaphore permit counter > 0.
STAGE 2
Charging
EV acquires permit.
Critical Section active.
Battery fills (0% → 100%).
STAGE 3
Completed
Target SoC reached 100%.
Power automatically cuts off.
STAGE 4
Released
Cable unplugged.
sem.release() called.
Resets to Available.
Say this to Madam "The unique feature is our 4-stage lifecycle: Available -> Charging -> Completed -> Released, guaranteeing clean handoffs between vehicles."
4. Parallel Execution
Handling Same-Resource Contention
Scenario Explained
“What happens when 2 cars arrive in parallel and request the exact same charging point (Bay 01)?”
1. Mutual Exclusion (Mutex)
• Both threads arrive at the exact same millisecond.
• Physical hardware is non-shareable: Mutex lock grants Bay 01 to Car A.
• Car B encounters conflict and is placed in the BLOCKED state (sleeps without CPU spinning).
2. Conflict Resolution Feature
• Dashboard displays conflict alert: Car B BLOCKED on Bay 01.
• Resolve Button: Clicking “Remove Conflict” dynamically reroutes Car B to free Bay 02!
• Result: Eliminates deadlock and charges both cars simultaneously.
Say this to Madam "When 2 cars request Bay 1 in parallel, Mutual Exclusion serializes them: Car A charges while Car B blocks. Our resolve button can dynamically reroute Car B to Bay 2."

Spawning 5 concurrent threads students = ["S1", "S2", "S3", "S4", "S5"] threads = [] for student in students: t = threading.Thread(target=use_computer, args=(student,)) threads.append(t); t.start() # 5. Barrier synchronization for t in threads: t.join() print("All requests completed")
